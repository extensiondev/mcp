## extension_auth

Sign this machine in to extension.dev, report that login, or clear it: action status (the default), login and logout. Status names the workspace and project the stored token is scoped to and when it expires, never the token itself; that identity comes from the stored token alone and does not change with the current working directory, and the platform's whoami endpoint is asked whether the credential resolves there, answered in value.server.verdict as confirmed, refused or unavailable, so a local file claiming a login the server refused is never reported as logged in. Login is two-phase: call with `project` to get a code plus a URL the user authorizes at extension.dev/device, then call again with the returned `deviceCode`; GitHub federation happens server-side, so no GitHub token lands on this machine. Minted tokens live at most 7 days, server-enforced, so CI must re-mint before expiry on the console's project settings, Access tokens page. Not for a project that does not exist yet: that is extension_project_create. Several logins live side by side, one per server and workspace/project, and a call uses the login minted on the server it targets (`api`, else EXTENSION_DEV_API_URL, else production), so a local dev login never stands in for a production one. To sign in to several existing projects at once pass `projects` instead of `project`, or `workspace` with projects:"*" for every project a workspace has: one approval, one stored token per project. A project renamed in the console keeps its login: the next call notices, moves the login to the new <workspace>/<project> and says so once; a not-found answer from an older platform means list the workspace through another login and log in to the new slug.

| --- | --- | --- | --- | --- |
| `action` | "status" \| "login" \| "logout" | no | `"status"` | status (the default) reports the default login for unnamed calls and lists every stored login under `logins`, each with its server, workspace, project, expiry and whether it is the default, plus the server's own verdict on the token it reports; with `project` it reports that project's login instead, verified with that login's own token, and answers not-signed-in when none is stored for it. login signs in: the first call answers a code and the URL to authorize at extension.dev/device, the second, with `deviceCode`, stores the token; with `projects` or `workspace` it stores one token per project under one approval, and the answer names each project signed in. logout deletes the local credentials only (with `project`, just that project's login); the token stays valid server-side until it is revoked at the URL the answer returns. |

## extension_build

Build a browser extension for production. This tool always passes --browser (chrome unless you set it), so the output lands in dist/<browser>/ (dist/chrome by default) and the answer's outputPath always names the folder that was written (the engine's reported path, else dist/<browser> under the package root, the same folder this tool checked for the manifest), with zipPath beside it when a zip was asked for: read those paths instead of assuming one. To know what is in the build (sizes, entry points, the checks a store reviewer runs) call extension_analyze on the same projectPath and browser instead of listing or reading the output folder by hand; the answer's hint says so. A scaffolded project's own `npm run build` runs `extension build` with no --browser, which the engine defaults to chromium, so that script writes dist/chromium/ instead. Pass zip:true to also package a .zip for store submission. With browser:'safari' the build converts the extension into a macOS app through Xcode, and bundleId sets the identifier it ships under. The build refuses a manifest with build-blocking errors unless you pass skipValidation:true, because such a manifest yields a broken bundle the bundler itself never flags.

## extension_builds

Read, download, rebuild and configure the platform's builds of the logged-in project on extension.dev: action list (the default), get, logs, download, recheck, rebuild, configure, create-channel, configure-channel and delete-channel. The three reads change nothing; download saves a build's package to disk through the platform, verified against its integrity report, for a store upload done by hand; the acts change the project, and every one of them answers what the platform recorded in value.outcome and the links it made or touched in value.links, waiting up to waitSeconds for the record and answering rebuild-dispatched or recheck-dispatched until it confirms. Every answer links the console page it is about in value.trackUrl; failure details (the failed step, annotations, last lines) come back as data, and the build page shows the rest. Not for reading channels, release history or store submissions: that is extension_release_status. Not for reading the build settings: that is extension_workspace action:'settings'. A rebuild spends the workspace's build allowance and is rate limited. Rebuild, recheck, configure, a private channel and a channel's fields are plain calls under the owner's own token, with this client's permission prompt as the gate; a public channel audience keeps the approve page, and a channel delete stays in the console. This uses the stored login for the project (extension_auth), against the server the call's api names.

## extension_create

Create a browser extension project from a template in the extension.dev catalog; call extension_templates first to see what is available. ## extension_wait

Use it before extension_project_create when the project's workspace is not there: project creation can only target an existing workspace, and this tool is what brings one into existence. Two-phase, like login: the first call returns a code and a URL where a signed-in GitHub user approves creating exactly this workspace and becomes its owner; call again with the returned deviceCode to finish. Check `ownerGithubLogin` in the answer: whoever approved the code owns the workspace. The approval mints a grant that lives minutes, can only create the one named workspace, names no project, and is kept on this machine only while a create's outcome is unknown: then it sits in a file only this user can read, beside the stored logins, so calling again with the same deviceCode reads that outcome with no second approval. Then run extension_project_create against '<workspace>/<project>'.

| input | type | required | default | description |
| --- | --- | --- | --- | --- |
| `workspace` | string | yes |  | Slug of the new workspace, lowercase letters, digits and hyphens, no slash. It must not exist yet; a personal workspace (the GitHub login) already exists for every signed-in user, so this is for a shared or organization-style workspace. |
| `displayName` | string | no |  | Human name for the workspace. Defaults to the slug. |
| `description` | string | no |  | Short workspace description. Optional. |
| `developerUrl` | string | no |  | Public URL for the workspace. Optional. |
| `deviceCode` | string | no |  | Resume token from the prior call's `deviceCode`; omit on the first call. |
| `api` | string | no |  | Platform base URL (default EXTENSION_DEV_API_URL, else https://www.extension.dev) |
